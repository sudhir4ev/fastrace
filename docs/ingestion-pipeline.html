Fastrace - Ingestion Pipeline

How a BLF trace becomes a queryable Trace Store, how the Trim Window scopes every read, how signals are decoded on demand, and how the pipeline keeps disk I/O to the minimum. This is the authoritative picture of the target design; vocabulary matches CONTEXT.md, boundaries match docs/adr/0001.

1 · The BLF on disk

A BLF file is a LOGG file header followed by a sequence of LOG_CONTAINER objects. Each container is a single zlib-compressed blob (inflated with libdeflate). Inside a container, once inflated, is a run of LOBJ objects - the actual CAN / CAN-FD / Ethernet messages.

Why you cannot read a timestamp without inflating

Every message carries a uint64_t timestamp in its BlfObjectHeader. But that header lives inside the container's single zlib stream - headers and payloads alike. There is no object-level compression and no time range in the container header. So to learn even one message's timestamp you must inflate the whole container.

Consequence: the dominant cost of ingestion is inflate (zlib + paging bytes off disk), not payload parsing. Any optimization that still inflates a container has already paid the bill. The only way to make a windowed read cheaper is to not inflate out-of-window containers at all.

2 · Prepare - the one write pass

fastrace_parse prepare <trace.blf> [trace.arxml] runs a single BlfIngestReader::visit pass. Each container is inflated once; its messages flow through the DuckDB Appender into the Trace Store. On any failure the partial .duckdb is deleted (fail-fast).

new container_index is built for free. Prepare is already inflating every container, so it also records, per container, its byte offset, its first / last message timestamp (coarse), and its first global msg_id. One extra Appender, no extra read.

3 · The Trace Store tables

The Trace Store is a DuckDB file beside the BLF. The Rust app opens it read-only and checks schema_version (currently 5). The C++ sidecar is the only writer.

4 · Trim - scoping every read, non-destructively

The Trim Window is a [start, end] in timestamp_us. It never mutates the BLF or deletes rows - it only bounds what queries return and what gets decoded. The user sets it two ways (a toggle on the header slider):

Time-based

Drag the start/end timestamp handles directly.

Message-based

Pick start/end by ordinal position ("message 30 → 50"); resolved to timestamps at Apply time.

Internally the window is always [start, end] in timestamp_us - the backend has no notion of "strategy."

Turning a window into a byte range

The container_index makes a window a seek, not a scan. Only the containers whose coarse range overlaps [start, end] are inflated; everything before is skipped, everything after triggers an early stop.

startOffset = max(byte_offset) where first_ts_us ≤ start · endOffset = min(byte_offset) where first_ts_us > end (or EOF). A precise per-message ts gate inside the pass trims the partial first/last containers. Coarse container timestamps are enough to decide what to skip - that was the whole point.

5 · Signals - decoded on demand, incrementally

Signal values are not decoded at Prepare (docs/adr/0005) - only when the user reads payloads for a signal. Decoding walks the in-window containers, runs decodeAllSignals per message, and appends samples to signals.

signal_coverage: never decode the same message twice

Each decoded signal records the single contiguous window its samples cover. On Apply, that window decides what, if anything, to read:

  • Expand → decode only the uncovered delta (one or both edges), append, extend coverage to the union.
  • Shrink → decode nothing; the existing samples are simply filtered by timestamp_us in SQL.
  • Disjoint jump (new window doesn't overlap coverage) → delete the stale samples and re-decode the new window, resetting coverage. (Rare; keeps coverage a single contiguous range.)

Decode-only apply-trim

A single apply-trim subcommand, in one visitRange over the in-window containers, appends the decode delta for the active signals. signal_stats stay Prepare-time / full-trace and are not recomputed. Shrink / already-covered / empty active set skips the BLF walk. "Read Payloads" uses the same pass.

6 · How we keep I/O minimal

before (per Apply) after (per Apply)
2 × full fileOld: signal-stats then decode-signals, each inflating the entire trace - even on shrink.
1 × windowNew: one decode-only apply-trim pass inflating only overlapping containers.
0 re-readsCovered ranges are never re-inflated; shrink / no active signals read nothing.

The four levers

  1. Index, don't scan. container_index turns a window into a seek - out-of-window containers are never inflated.
  2. Decode only on Apply. signal_stats stay Prepare-time; Apply never re-observes the catalog.
  3. Incremental decode. signal_coverage means expand reads only the delta and shrink reads nothing.
  4. Coarse is enough. Container-level timestamps (captured once at Prepare) decide what to skip - no per-message index, no extra read.
Why Apply got slow mid-migration: trim briefly added a dedicated signal-stats recompute on every Apply (and later folded it into apply-trim), so "Read Payloads" paid catalog-observe cost on top of decode. Stats are Prepare-only again; Apply is decode (+ coverage) only.

7 · Known gaps & deferred work

  • decodeAllSignals is CPU-wasteful (KIV): for each message it decodes every signal on the frame, then filters to the requested ones. This is CPU, not I/O, so it doesn't affect read volume - but it is the next optimization after this wave (share the tracker's decode with the append path).
  • Leading-edge split objects: a message straddling the boundary into the first inflated container may be dropped (no stitch tail on a mid-file start). Its timestamp is almost always below the window; at most one edge sample is lost. This is the agreed coarse tolerance.
  • list_ecus is not trim-scoped: arxml_ecu has no schema link to any frame/PDU/timestamp, so the ECU list always shows the full ARXML dictionary.
